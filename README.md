🤖 AI-Agent Test Automation Pipeline (Doc-to-Test) An end-to-end autonomous test engineering ecosystem: A multi-agent automation architecture that analyzes raw business requirement documents (.xlsx / .docx), explores live web pages using Playwright, generates Java/Playwright BDD test code through deterministic contracts, self-heals compilation errors at the Maven level, and pushes the test suite to GitHub Actions.

📌 Project Origin & Solved Industry Problems
Traditional LLM-based code generators produce non-functional and unmaintainable test automation code in practice. This project solves the following core challenges:
* **Hallucination-Causing Fake Classes:** Prevented models from calling non-existent classes (DriverFactory, ReusableMethods, org.junit.*); locked the architecture entirely onto TestNG, BasePage, and PicoContainer.
* **Blind Locator Generation:** Instead of fragile CSS/XPath selectors guessed without seeing the page, the Planner Agent inspects the DOM and Accessibility Object Model (AOM) in a live browser to determine semantic and real selectors (getByRole, getByPlaceholder).
* **IDE and Cucumber Expression Mismatch:** Escaping errors in quotation marks causing steps to remain yellow and undefined (Undefined Step) in IntelliJ/Eclipse were fundamentally resolved via dynamic {string} contracts.
* **Compilation Loop Fatigue:** Enabled generated code to self-heal through micro-patches without human intervention via the Healer Agent, which is fed by Maven compiler (mvn test-compile) outputs.

🧩 Step-by-Step Execution Lifecycle
1. Document Processing & User Story Extraction (Stage 0)
Files (.docx or .xlsx) dropped into the input_docs/ directory are parsed using openpyxl and python-docx engines.
Messy data and revision notes in raw tables are filtered out and transformed into clean Business Rules and testable User Story formats.

2. BDD Feature Generation & Regex Sanitization (Stage 1)
The extracted story is converted into a complete Gherkin .feature text.
Deterministic Sanitizer: Bracket complexities, markdown remnants, and quote errors that could be produced by the LLM are cleaned using Python Regex with zero token consumption.

3. Cucumber CLI Official Contract (Stage 2.5)
After the feature file is saved to disk, mvn test -Dcucumber.execution.dry-run=true is executed in the background.
Official Java method formulas ("Snippets") generated by the Cucumber CLI engine are pulled directly from the CLI output. This list acts as a binding contract for the model in the next stage.

4. Planner Agent: Live Web Discovery (Stage 3)
Playwright Chromium is launched in headless mode and navigates to the relevant URL in the scenario (e.g., /login, /virtual-staging, /register).
Buttons, text boxes, links, and placeholders in the page's AOM (Accessibility Object Model) tree are extracted.
The Planner correlates Gherkin steps with live elements to produce a clear Execution Plan in JSON format.

5. Generator Agent: Java Test Class Generation (Stage 4)
Runner: The TestNG Runner class is written to disk using a deterministic pure Java template to prevent potential LLM syntax errors.
Pages Class: A Page Object class extending BasePage that utilizes AOM selectors (getByRole, getByPlaceholder) and ready framework methods (myClick, mySendKeys).
Steps Class: Bases on the Cucumber CLI contract, binds objects via PicoContainer Constructor Injection (TestContext), and handles dynamic data with {string} parameters.

6. Healer Agent: Autonomous Compilation & Micro-Repair (Stage 5)
The mvn test-compile command is executed.
If a compilation error occurs (e.g., cannot find symbol, incompatible types), the tail of the error log is extracted.
The Healer Agent analyzes the source of the error, returns the repaired code exclusively for the corresponding Page or Step class, and overwrites the file. Up to 3 attempts are executed until the build reaches BUILD SUCCESS.

7. Git Synchronization & CI/CD Handoff (Stage 6)
Only code passing the Maven compilation test is committed and pushed to the repository via git add ., an automatic timestamped git commit, and git push origin main.
The triggered GitHub Actions workflow executes tests in headless mode on the cloud and generates reports.

🛠️ Technology Stack and Integrations
| Layer | Tool / Technology | Role / Responsibility |
|---|---|---|
| **Agent Framework** | Python 3.10+, Google GenAI SDK | Agent orchestration, decision mechanisms, and API communication |
| **Development & Protocol** | VS Code, PyCharm, Model Context Protocol (MCP) | Virtual environment management, context standardization, and file system operations |
| **Live Page Analysis** | Playwright Python | Headless DOM and AOM tree scanning, element metadata extraction |
| **Test Framework** | Java 11+, TestNG, Cucumber | BDD scenarios, assertion structures, and execution management |
| **Browser Automation** | Microsoft Playwright Java | End-to-end UI test execution over the Page Object model |
| **Dependency Injection** | Cucumber PicoContainer | Thread-safe data transfer and inter-scenario TestContext management |
| **Compilation & Validation** | Apache Maven | Build validation and CLI contract extraction via CLI |
| **Document Parsing** | openpyxl, python-docx | Reading .xlsx and .docx business requirements |
| **CI/CD** | Git, GitHub Actions | Automated commit, push, and remote execution of validated code |

🛡️ Resilience Layer
Exponential Backoff & API Protection: Requests are not dropped on 503 Unavailable or 429 Resource Exhausted errors; the system waits with exponentially increasing intervals (5s, 10s, 15s...), safeguarding the API window.
Model Fallback Layer: During high traffic, the system automatically switches to the next stable Gemini model.
Broken Code Prevention: No scenario failing the compilation stage is pushed to the repository; the main branch is always kept in a working state.
